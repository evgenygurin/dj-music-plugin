# Правила документации

Документация является объяснением устойчивого поведения системы, а не копией текущего состояния репозитория.

## Что фиксировать

Фиксируй только:

- архитектурные границы и инварианты;
- публичные и межслойные контракты;
- причины важных решений;
- устойчивые workflow и ограничения;
- правила безопасности и эксплуатации, которые нельзя потерять при рефакторинге.

## Что не фиксировать вручную

Не дублируй без необходимости:

- количество tools, resources, prompts и зарегистрированных сущностей;
- количество тестов, coverage и другие результаты конкретного запуска;
- количество файлов, символов, связей и execution flows;
- текущие версии/пины, если они уже являются source of truth в manifest или lockfile;
- каталоги runtime surface, которые можно получить через framework discovery;
- временные workaround'ы, закрытые миграции и исторические состояния.

## Source of truth

Порядок доверия при расхождении:

1. исполняемый код и схемы;
2. manifests/configuration, определяющие runtime;
3. автоматические тесты и validators;
4. актуальные нормативные rules/docs;
5. historical reports, research и audit snapshots.

Если документ намеренно описывает историческое состояние, укажи это в его заголовке или названии. Не переписывай историю, чтобы она выглядела текущей.

## Избегай каскадных обновлений

Добавление runtime-объекта не должно требовать ручного обновления нескольких документов только ради изменения счётчика или списка. Такие данные должны быть derived, автоматически проверяться или вообще не документироваться.

## README

README отвечает на вопросы: что делает проект, как запустить, какие фундаментальные возможности он предоставляет и где искать подробную документацию.

README не является полным API catalog и не должен содержать snapshot текущего числа runtime объектов.
