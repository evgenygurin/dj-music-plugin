# DJ Music Plugin — Project Instructions

> MCP-сервер для управления DJ-библиотекой, анализа аудио, построения и доставки DJ-сетов.

**Язык:** отвечай по-русски, если пользователь не попросил иначе.

## Инструменты и проверки

- Используй `uv` для установки зависимостей и запуска Python-инструментов.
- Основной quality gate проекта — `make check`.
- Перед отправкой изменений учитывай repository hooks и выполняй релевантные проверки.
- Не обходи проверки ради зелёного статуса: исправляй причину или явно фиксируй остаточный риск.

## Архитектурные инварианты

- FastMCP — внешний интерфейс приложения.
- `app/domain/` содержит чистую предметную логику и не зависит от DB, HTTP или FastMCP.
- `app/tools/`, `app/resources/` и `app/prompts/` формируют MCP surface; реализация и состояние находятся ниже этого слоя.
- `app/repositories/` отвечает за доступ к данным; границы между domain и infrastructure сохраняются.
- Audio/DJ orchestration должна оставаться отделённой от transport и persistence.
- Новые возможности должны встраиваться в существующие bounded contexts, а не создавать параллельную архитектуру без необходимости.

Подробная архитектурная политика: [`rules/architecture.md`](rules/architecture.md).

## GitNexus

Используй GitNexus для навигации и оценки влияния перед изменением существующих символов. Перед коммитом проверяй фактический scope изменений.

Подробный workflow: [`rules/gitnexus.md`](rules/gitnexus.md).

## Документация и агентские правила

Документация должна фиксировать только устойчивые знания: архитектурные решения, инварианты, контракты, границы ответственности и рабочие принципы.

Не дублируй вручную volatile runtime inventory: количество tools/resources/prompts, число тестов, текущие counts файлов, внутреннюю статистику индекса, временные версии и другие данные, которые меняются вместе с кодом.

Когда факт можно надёжно получить из кода, manifest'а, FastMCP introspection или quality gate, предпочитай источник истины вместо ручной копии.

`AGENTS.md` — только router и критические инварианты. Подробные правила находятся в `rules/`; доменные детали — в соответствующих `docs/`.

## При изменении MCP surface

Проверяй фактический runtime contract и существующие schema/registration tests. Не поддерживай отдельные ручные каталоги только ради документального перечисления runtime-объектов.

## При изменении audio/DJ engine

Сохраняй разделение анализа, кандидатов, scoring, planning, rendering и persistence. Новые engine modes должны быть rollout-safe, если изменение касается существующего production path.

## История и research

Исторические отчёты, планы, research notes и audit snapshots не являются текущим source of truth. Не переписывай их задним числом только для придания им видимости актуальности.

## Базовый маршрут агента

1. Прочитать этот файл и релевантные правила.
2. Найти фактический implementation contract в коде и тестах.
3. Оценить влияние изменений до правки существующих символов.
4. Внести минимальное изменение.
5. Выполнить релевантные проверки.
6. Перед коммитом проверить scope изменений и documentation drift.
